# Project Memory

## Locked Decisions
- **Application Type:** Actual Android mobile application (Not a web frontend).
- **Mobile Stack:** React Native, Expo, TypeScript.
- **Backend Stack:** Node.js, Express, TypeScript.
- **Database Stack:** MongoDB, Mongoose.
- **Authentication:** Passwordless Email OTP (No passwords, no forgot password flows).
- **Roles:** `STUDENT` and `ADMIN`.
- **Branding:** GIET(A) branding. The official GIET(A) logo is the brand source of truth.
- **Design Language:** Minimal, lightweight, clean, professional, and institutional. No unnecessary gradients, shadows, or visual clutter.
- **Design Source of Truth:** The provided reference images.
- **Security:** Backend is the source of truth for all security and business rules (capacity, duplicate checks, role access).
- **Scope:** Do not introduce unnecessary features not listed in the PRD.
- **Phase 1 Auth Decisions:** OTPs are 6-digit random numbers, hashed via bcrypt before storage in MongoDB. Valid for 5 minutes. Max 3 failed verification attempts before invalidating. Resend cooldown of 1 minute. Email delivery is mocked in development via terminal logs, ready for SMTP config in production. Mobile app uses `expo-secure-store` to keep the JWT token safe. Completing the profile is strictly required for new students immediately following verification.
- **Phase 2 Profile & RBAC Decisions:** Mobile routing handles role logic at the `RootNavigator` level (`AuthNavigator`, `CompleteProfileScreen`, `AdminNavigator`, `StudentNavigator`). Backend is strictly the source of truth for authorization (`authenticate`, `authorize([ROLE])`). Axios is set up to append bearer tokens automatically and intercept 401 Unauthorized for smooth logout flows.
- **Phase 3 Event Discovery Decisions:** DRAFT events are strictly blocked on the backend for students. The event API uses MongoDB `$text` search index for fast querying by title/description and sorts appropriately. Mobile screens include robust pagination/pull-to-refresh implementations via FlatList, and the EventDetails screen serves as a placeholder until Phase 4 brings registration functionality.
- **Phase 4 Registration Decisions:** MongoDB enforces one registration per student/event via a unique compound index `{ student: 1, event: 1 }`. Capacity checks and duplicate verifications run in Mongoose sessions/transactions. The API returns an `isRegistered` flag on event details allowing UI to reactively disable the register button. The `RegistrationDetailsScreen` holds basic info.
- **Phase 5 QR Pass Decisions:** Secure pass generation utilizes Node.js `crypto.randomBytes(32)` to generate an unguessable 64-character hex token exactly once during registration. The raw token is stored in the `qrToken` field on the Registration model, safely unassociated with sensitive authentication tokens. The `/api/registrations/:id/pass` API ensures strictly scoped ownership before exposing the pass. The Mobile app uses `react-native-qrcode-svg` to generate the code natively without third-party web generation services, protecting privacy and performance.
- **Phase 6 Admin Event Management Decisions:** Admin operations are siloed in `adminEventController` and `/api/admin/events` routes to ensure clean separation of privilege. The backend strictly enforces `DRAFT`, `PUBLISHED`, and `CANCELLED` lifecycle. Publish operations validate capacity (>0) and required fields natively. Capacity edits reject values lower than current live registrations to prevent invalid state. The mobile app incorporates an `AdminNavigator` stack holding `AdminTabs`, `CreateEvent`, `EditEvent`, and `AdminEventDetails`. Action buttons strictly depend on backend state (e.g., Publish is only visible for DRAFTs). Students' `getPublishedEvents` cleanly filters out DRAFTs by only accepting `PUBLISHED` or `CANCELLED`.
- **Phase 7 Attendance & QR Scanner Decisions:** Attendance tracks natively on the `Registration` schema (`checkedIn`, `checkedInAt`, `checkedInBy`). An admin must be in the context of an event to scan via `ScanAttendanceScreen` which securely calls `POST /api/admin/events/:eventId/check-in`. The backend enforces duplicate checking (rejecting already checked in), strict cross-event protection (QR must belong to `:eventId`), and prevents scanning unpublished events. The Mobile layer uses `expo-camera` securely within the stack. Student-side dynamically shows "CHECKED IN" or "NOT CHECKED IN" natively in `RegistrationDetailsScreen.tsx` without needing dedicated new models.
- **Phase 8 Notifications Decisions:** Notifications are strictly in-app via a `Notification` model with explicit `recipient` ownership. The backend triggers notifications internally without exposing creation endpoints to clients: `REGISTRATION_CONFIRMED` upon successful registration inside a session transaction, `EVENT_UPDATED` and `EVENT_CANCELLED` upon relevant admin edits (only notifying actively registered students), and `ATTENDANCE_CONFIRMED` upon successful QR check-in (ensuring duplicate scans do not create duplicate notifications). The mobile app places a `NotificationBell` in the `StudentTabs` header, resolving unread counts dynamically. Viewing details marks the notification as read server-side, preventing duplicate API calls. Notifications offer deep navigation to `EventDetails` or `RegistrationDetails` avoiding duplicated screens.
- **Phase 9 Feedback & Rating Decisions:** Feedback Eligibility is enforced explicitly via the backend. Registration verification ensures the `checkedIn` flag is true before allowing `Feedback` creation. Feedback uniqueness is managed via a `{ event: 1, student: 1 }` database index and duplicate-key error trapping (409 Conflict) preventing race conditions. Client Side Validation intelligently hides the "Give Feedback" button dynamically by returning `hasFeedback` implicitly inside `getRegistrationDetails` allowing the mobile frontend to stay dumb without redundant API calls.
- **Phase 10 Profile & Settings Decisions:** Settings focus strictly on essential Session control. The `PATCH /api/profile` securely parses out non-editable fields (like `role` or sensitive auth data) preventing privilege escalation. Navigation seamlessly handles updates via `useFocusEffect` hooks that refetch profile details instantly upon popping from the `EditProfileScreen`, circumventing complex global state setups like Redux while feeling instantaneous. Logout delegates to `AuthContext` by wiping `SecureStore`, implicitly crashing the protected `RootNavigator` state safely back to the Auth screen without token invalidation network overhead.
- **Phase 11 Security & Reliability Decisions:** Integrated `helmet` and `express-mongo-sanitize` globally to prevent injection attacks and XSS. Implemented `express-rate-limit` strategically: global limiter of 100 reqs/15m across `/api`, with strict thresholds for `request-otp` and `verify-otp`. Pagination parsing strictly validates `page` and `limit` to prevent NoSQL injection via limit properties. Verified OTP systems properly mark codes as `consumed` within secure expiration windows. Audited Registration logic heavily relying on Mongoose `$session` transactions to reliably prevent capacity race-conditions natively on the database layer. JWT and Server configurations audited correctly exposing nothing out of `.env.example`. Mobile endpoints properly prevent duplicate submissions client-side via UI loading states.
- **Phase 13 Release Build & Preparation Decisions:** App identity confirmed as "GIET(A) College Event Management" with package `com.gieta.events`, version 1.0.0 (versionCode 1). Permissions strictly limited to CAMERA (for admin QR check-in) and INTERNET, with microphone and audio permissions removed. Centralized `api/client.ts` supports `EXPO_PUBLIC_API_URL` environment variables. Backend server connects dynamically to MongoDB via `MONGO_URI`, implements Express 5 compatible Mongo sanitization, and permits native mobile cross-origin requests. Release profiles configured via `eas.json` for APK (`preview` / `production-apk`) and Play Store AAB (`production`). Keystores, signing keys, and release binaries strictly excluded from source control.
- **Stage 1 Testing Audit Decisions:** Registration routing must scope `studentAuth` middleware to individual registration endpoints rather than using router-level `router.use()` when mounted at root `/api`, preventing route bleeding into `/api/admin/*`. Registration transactions dynamically detect connection topology (`isReplicaSet`) to ensure full ACID multi-document transactions on replica sets while providing graceful fallback to atomic queries and unique index constraints on standalone developer instances. Check-in notification dispatch safely extracts `studentId` from populated student documents to prevent Mongoose ObjectId CastErrors.
- **Infrastructure & Email Service Decisions:** Primary database is hosted on MongoDB Atlas cloud replica set (`collegeeventmanagermobi`), enabling native ACID multi-document transactions in production. Production email delivery utilizes Nodemailer via Gmail SMTP (`smtp.gmail.com:587` with TLS) authenticated with a dedicated Google App Password, allowing real-time OTP delivery to `@giet.edu` student inboxes while falling back to console mock delivery in offline/local environments if SMTP is unset.
- **Phase 14 Institutional Branding & Student Profile Decisions:** OTP emails employ rich institutional HTML templates with GIET (Autonomous) insignia, institutional colors (Navy `#0E526B`, Crimson `#DC2626`, Gold `#F59E0B`), and security notices. Onboarding captures academic metadata (Roll Number, Department/Branch, Academic Year, and Phone Number). Header greetings parse the user's first name dynamically instead of raw email addresses. Profile navigation is centralized strictly in the bottom navigation tab bar, eliminating duplicate header avatars and shortcut cards.
- **Phase 15 Executive Admin Portal Decisions:** Admin navigation uses custom vector SVGs (`DashboardTabIcon`, `EventsTabIcon`, `AttendanceTabIcon`, `UserTabIcon`) instead of raw emojis. The Admin Dashboard avoids vertically stacked statistic cards by utilizing a unified, compact 4-column Horizon Metric Bar with direct tap-to-filter navigation, an Executive Command Banner with 1-tap event creation and pass scanning, and a 2x2 responsive Command Grid. Cancelled events in `AdminEventDetailsScreen` support recovery via "Restore Event to Draft" and "Edit Event Details" actions.
